> 区分两种台账：
> - **运行时台账**：`<用户数据目录>/state/audit.jsonl` —— 工具每次 plan / apply / verify / restore 自动记
> - **本文件** —— 记录**开发与验证过程中**对本机真实 WorkBuddy 的写操作
>
> 铁律 1：无备份不成写。每条都必须写明**备份 id、还原结果、逐字节校验**。

## 本篇主张

工程期动过三次真实文件，**全部已还原、留了备份、逐字节校验过**。这篇是那个「已还原」的凭据——不是声明，是每一条都能对到具体的备份 id 与 sha256。

反面：**备份不等于永远可用**。整理工作区时我删过一份冗余备份，下面「备份现状」一节如实登记了这件事。凭据会腐坏，所以台账要带失效登记，不能只记「当时还原了」。

## 备份现状（含失效登记）

台账的价值取决于凭据还在不在。截至 2026-11-01：

| 备份 id | 位置 | 状态 |
|---|---|---|
| `20261031T182933Z-aa05bc` | `<用户数据目录>/backups/` | ✅ 可用（app-config.json，`897d5afb…`） |
| `20261031T183925Z-508ba5` | `<用户数据目录>/backups/` | ✅ 可用（style-socratic.md，`879c83bb…`） |
| `20261031T183000Z-8d7934` | 原在 `.local-store/backups/` | ⚠️ **已删除** |

**关于第 3 条**：2026-11-01 清理工作区（`.local-store/` 从 2.6 MB 降到 0.12 MB）时，该目录下的 4 份测试备份被判定为"冗余副本"一并删除。当时的判据是——**4 份都是同一原始 SOUL.md 的副本，且与当前文件逐字节一致**（`5602F4B6…` / 1091 B），说明文件已完好还原，备份只是冗余。

事后核对：**SOUL.md 当前仍为 `5602F4B6…`，未受影响**。但该备份本身已不可恢复——**这正是「删除冗余备份」的代价**：它当时确实冗余，但复查凭据少了这一份。

**教训**：清理测试产物时，「冗余」的判据要看**未来是否可能被要求复盘**，不只是「内容是否重复」。这条记在这里而不是忘掉。
