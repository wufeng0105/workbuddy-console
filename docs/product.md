# 产品：要什么

> 配套：[framework](framework.md)（怎么造）｜[verification](verification.md)（怎么证明）｜[handles](handles.md)（有哪些面）

## 本篇主张

这个工具解决一个具体的错配：WorkBuddy 把「能改什么」散在设置界面、隐藏配置、插件缓存、环境变量四处，而**改完之后它不告诉你生效没有**。工具把四处收拢到一处，并为每一步补上两样东西——**代价预告**和**生效证据**。

反面：它**不提升可达性**。服务端过滤、模型自身对齐、托管策略回写，这三样客户端碰不到。工具能做的是**把边界画清楚**，让你不把时间浪费在碰不到的地方。

## 一句话定位

> WorkBuddy **宿主层**的个性化配置管理器 + 生效验证器：
> **改之前告诉你代价，改完证明它真的生效，升级后告诉你还在不在。**

**A（管理器）为体，B（验证器）为魂。** 没有 B，A 只是一个更好看的配置文件编辑器。

## 层边界

| 层 | 包含 | 姿态 |
|---|---|---|
| **宿主层**（客户端本体） | 配置存储、提示词组装、插件、沙箱规则、审批、启动参数 | **经营**：改、备份、还原、验证 |
| **上游层**（sidecar 之上的网关与模型） | 内容过滤闸、模型对齐、服务端下发的托管策略 | **只呈现**：如实写进边界说明，不改 |

### 四种"拒绝/询问"必须分清

这是产品最容易做错的地方——用户说"它不让我做"，可能指四件完全不同的事：

| 现象 | 层 | 能改吗 |
|---|---|---|
| 模型自己不愿答、说教、拒绝 | 上游 | ❌ |
| 模型答了、流被拦腰切断、usage 清零 | 上游（网关） | ❌ |
| 宿主弹审批 / 拦下工具调用 | **宿主层**（规则引擎 + 审批运行时） | ✅ |
| 模型在**回答文本**里问"要我先扫描还是直接改？" | **宿主层**（提示词层的 `personal_files_safety` 条款） | ✅（但**能否治住未验**） |

后两者是**独立的两层**：弹窗审批由规则引擎执行；模型在文本里问由提示词条款驱使。规则改完还偶尔被"问"，多半是第二种。

## 专家档位模型

**一个"专家" = `SOUL.md`（身份立场）+ `style-*.md`（表达方式）+ `toneStyle`（档位指针）**

**分工制**，不是二选一：

| 载体 | 负责 | 不负责 |
|---|---|---|
| `style-*.md` | 表达方式：语气、句式、结构、长度、要不要寒暄 | 你是谁、底线、领域 |
| `SOUL.md` | 身份与立场：你是谁、和我的关系、底线、领域偏好 | 表达方式 |

二者是 user-context 模板里的**两个不同变量**（`{{ ToneStyleContent }}` / `{{ SoulContent }}`），同时渲染进同一段，**没有技术上的覆盖关系**。所谓"冲突"，真相是两份指令同时摆在模型面前——**只有两边都写表达方式时才会打架**。

### 两个必须建模的硬约束

| 约束 | 后果 |
|---|---|
| **注入上限 10 000 字符 / 文件** | 超出部分**静默丢弃**。**"文件写了" ≠ "模型看到了"** → `verify` 的期望增量必须按**截断后**文本算 |
| **专家模式跳过 `IDENTITY.md`** | 切档位时"名字"**静默消失**；SOUL 与 USER 两模式都注入 |

### 其他要点

- **7 是风格槽位数，不是专家数上限**。真正的限制是「同时只有一个专家生效」。
- **切换必须同时改 SOUL.md**：`toneStyle` 只决定读哪个 `style-*.md`，SOUL.md 不会跟着切。
- **提权成本可摊薄**：`toneStyle` 与 `SOUL.md` 在用户目录 → 日常切换零提权、零停机，仅需新会话生效。只有 `style-*.md` 的内容在 `Program Files` → 7 份预装配一次（提权 1 次），升级后若被还原再走一次重放。

## 越界行为：四个档位

**白名单 / 黑名单 / 分级不需要发明——它已经存在。**

```
sandbox.orderedRules
  三域：file / command / network
  每条 = { 路径/模式, isDirectory, read, write, delete }
                                    ↑       ↑       ↑
                              各可 allow / ask / deny
```

本机实测：file **135** 条（read: allow 133 / ask 2；**write: allow 86 / ask 49**）；command **0** 条；network **0** 条（语义待实测）。

**那 49 条 `write=ask` 就是要放开的东西；路径粒度就是"黑名单"能力。**

| 档位 | 宿主规则面 | 提示词面（`personal_files_safety`） |
|---|---|---|
| **原厂** | 135 条原样 | 原样 |
| **放宽**（建议默认） | 49 条 `ask` → `allow`；凭据类目录（`~/.ssh/` 等）仍 `ask` | 保留 No-Go Zones；去掉 "Scan = Read-Only" / "模糊先问" 这类**强制询问**条款 |
| **全放开** | 全 `allow` | 整段移除 |
| **自定义** | 用户逐条改矩阵 | 用户自己编辑文本 |

> ⚠️ **诚实边界**：改提示词能**降低**"模型问"的概率，**不能保证**。若"模型问"来自模型自身对齐（上游），改提示词无效。
> 「能不能治」本身就是一个待验证假设——**把「治不了」如实报出来，才是这个产品最硬的价值**。

## 范围

### 纳入

| 把手 | 位置 | 提权 | 升级 |
|---|---|---|---|
| 称呼 / 名字 / 人设（USER / IDENTITY / SOUL） | `~/.workbuddy/user-<uid>-personal/` | 否 | 存活 |
| 指令（`customPrompt`）、回复风格（`toneStyle`） | `~/.workbuddy/app/app-config.json` | 否 | 存活 |
| `style-*.md` 内容（七档） | `C:\Program Files\WorkBuddy\...\templates\style\` | **是** | **疑失效**（待实测 #6） |
| 插件缓存模板 / fragments | `~/.workbuddy/plugins/cache/workbuddy-builtin/<plugin>/<版本哈希>/` | 否 | **失效** |
| 宿主规则矩阵 + 审批配置 | `~/.workbuddy/settings.json` | 否 | 存活（启动是否覆盖待实测 #1） |

### 排除

| 排除项 | 原因 |
|---|---|
| **长期记忆** | 被产品开关禁用（`cloud_memory_disabled`），受开关 + 云端 gate 双重控制 |
| **my-experts 自建专家** | 本期不做 |
| **模型切换 / BYOK** | 只是界面切换，不作承诺 |
| **上游内容过滤** | 客户端碰不到 |

## 分期：竖切优先

> 原则：**先用最少的把手数，验证技术风险最高的假设**，再横向铺开。

| 期 | 内容 | 为什么排在这 |
|---|---|---|
| **P0** | 一个把手（SOUL）走完六步 + 验证器跑通 | 验证器是唯一无参照系可抄、风险最高、决定产品命脉的部分。不接上它，「管理器立住了」**无法被证明** |
| **P0b** | 从 trace 自动取基线/观测（按**会话**切分） | 把"手工填数字"变成"改完点一下" |
| **P0c** | 本地服务端（回环 + 一次性 token）+ 原生 ESM 控制台 | 让东西真正可用 |
| **P1a** | 其余个性化四项 + 两个把手工厂 | 同一条尾段通道，复用同一套验证 |
| **P1b** | N 套档位一键切换（**多把手事务**） | 官方 UI 给不了多个可切换人设——最硬的差异化 |
| **P1c** | `style-*.md` 七档内容把手 | 需提权；升级疑失效 → 为版本重放打底 |
| **P2a** | 插件缓存模板三模式 + **标记法验证** | 换到**头部**通道，版本哈希定位 |
| **P2b** | 宿主规则矩阵 + **重启后回读验证** | 「审批自动同意」的规则面 |
| **P2c** | 版本重放（bundle → drift → replay） | 存**锚点键**不存路径，升级换目录也能重新定位 |
| **P3** | 审批自动同意（**两个面编排**，逐面诚实报告） | 规则面可靠；提示词面**无法保证**——如实呈现这个差异 |

## 非目标

- 不改网关流量、不改 `app.asar`、不改 fuses（侦察已证明**没有必须改 asar 的场景**）
- 不写绕过上游内容过滤的**具体配方**（只记录边界位置）
- **不做通用平台**——服务于 WorkBuddy 这一个目标才活得久。通用化会把专属知识稀释成"可选适配细节"

## 置信度与限制

层边界、档位模型、范围：来自 `recon-baseline` 的实证结论，高。分期**已实现 P0–P3 全部十项**。

2026-11-01 追加一期（需求侧定版）：控制台前端按用户任务重构（六页、双按钮「应用 / 还原」），上线**最初基线**版本化账本。落地细节见 [framework](framework.md)「最初基线」。

### 一处必须更正的措辞

上面「已实现」在 2026-11-02 之前**只表示功能存在，不表示承诺兑现**。两轮独立复核（27 条问题）证明：
「有验证策略」不等于「策略能给出答案」——规则面的验证策略没有任何用户可达路径、
提示词模板的标记法对普通编辑必然判「未生效」、反向改动永远判不出「生效」，
而前端会**把用户正在编辑的内容在点「应用」前冲掉**（表现为"点了应用，提示备份 null，内容没变"）。

这些都不是缺功能，是**承诺与实现之间的空档**：界面在，链路也在，答案给错了。

当前状态：上述 27 条已全部修复并各配断言（见 [framework](framework.md)「前端不变量」与
[verification](verification.md)「判据何时会给出错答案」）。**但仍有两处承诺不能兑现**，
写在 [DOC-OUTLINE](../DOC-OUTLINE.md) 的「已知残余」里：标记法对普通编辑只能报「无法判定」、
`render-log` 策略有名无实。

两处**待实测**会影响产品承诺的准确度：`style-*.md` 升级是否被还原（#6）、提示词能否治住模型自己问（#4）。两者都在 [verification](verification.md) 的清单里。
