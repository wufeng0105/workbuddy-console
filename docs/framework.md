# 框架设计

> 配套：`product.md`（造什么）｜`verification.md`（怎么证明）｜`handles.md`（把手清单）

## 一、"框架"在这里是什么

**不是目录结构，是四条稳定契约。** 前三条让它"立得住"，第四条让它"动态"。

| 契约 | 回答什么 | 稳定性 |
|---|---|---|
| **把手契约** | 每个可变面如何被 探测→预览→备份→写→验证→还原 | 不随 WorkBuddy 版本变 |
| **状态契约** | "文档=断言"如何变成可检测的期望状态与漂移告警 | 同上 |
| **边界契约** | 谁能写、何时能写（互斥）、写完记哪（审计+还原） | 同上 |
| **演进契约** | 升级时如何**只加数据、不改框架** | 同上 |

## 二、为什么不能照搬任何一个现成框架

Ansible / Terraform / chezmoi 的共同前提是：**"目标状态由你定义，且资源可回读"**。本项目三条全不成立：

| 现实 | 后果 |
|---|---|
| 目标状态**不由我们定义**——厂商在改（A 组模板数 18→16、`toneStyle` 漂移均已实证） | 照搬"声明式目标状态"立刻失准 |
| 效果**不可直接回读**——提示词进了 LLM，trace 还截断在 20003 字符 | 无法像 Terraform 那样 `refresh` 读回真实状态 |
| 写操作**可能有窗口约束**——若 C 组模板运行中不可热改（**待实测 #3，尚未证实**），则需停机写 | 没有参照系处理"目标程序运行中拒绝写"，需要自建闸门 |

**所以正解是：借契约形状，自己长三块骨头——锚点层、验证层、闸门层。**

## 三、参照系选型

| 排序 | 参照 | 借什么 | 对上哪条契约 |
|---|---|---|---|
| **主选** | **chezmoi** | **source state → target state**；`diff` / `apply` / `--dry-run`；**`re-add`**（把现状吸回源）；`doctor`（体检） | 状态契约 + 专家档位仓 + 升级重放 |
| **次选** | **Terraform** | `plan` / `apply` 分离、**漂移检测**、**provider 版本化** | 状态契约 + 演进契约 |
| **三选** | **Ansible** | module 契约：幂等 + `--check` + `--diff` + `backup` | 把手契约 |
| **点借** | **Home Assistant** | `schemaVersion` + **迁移函数** | 演进契约 |
| **自研** | — | **验证层**（见第四节） | 产品的护城河 |

> **选型变过一次，留档**：最初主选 Ansible（当时产品形态未定，按"改配置带护栏"猜）。形态定为"**N 套专家档位 + 一键切换 + 升级重放**"后，核心抽象变成**源状态**，故 chezmoi 升为主选。
> **这是"形态决定参照系"的实例** —— 框架服务产品，不是反过来。

### 明确不选的

**Cockpit**（本机特权后端 + HTML 控制台）——形态对我们太重；它唯一的价值（特权分层）用一个更简单的手段解决：**产品自建权限分层（见第六节），不依赖系统级 broker。**

## 四、第五块：验证层（任何参照系都不覆盖）

Ansible 写完能读回文件确认；Terraform `refresh` 能读回云资源。**而我们写完文件，不知道它有没有进 LLM。**

这一块直接来自侦察期最贵的教训（**修正史 #1**：标记写进错存储 + trace 截断 → 误判"不进 LLM"，复测被推翻）：

- 验证是**可插拔的一等公民**，不是一个开关
- **每个把手适配器必须声明验证策略；未声明者不允许上线**（铁律 2）
- 输出恒为**三态**：生效 / 未生效 / **无法判定**
- 详见 `verification.md`

## 五、Core / Data 分层

```
Core（框架 · 少变）—— 四条契约的接口与执行引擎，不随 WorkBuddy 版本变
├─ 契约接口定义（把手 / 状态 / 边界 / 演进）
├─ 执行引擎：plan → apply → verify → audit
├─ 备份仓 + 还原
├─ 漂移引擎（期望状态 vs 实际状态）
└─ 锚点解析器（探测失败硬报错，绝不猜）

Data（数据 · 多变）—— 加把手 / 加版本 = 只加数据
├─ 每个把手一个 adapter（含验证策略声明）
├─ 每个 WorkBuddy 版本一份锚点表（schemaVersion + migrate）
└─ 每个把手一份断言表（文档结论 → 可执行期望值）
```

> **"立得住"** = Core 四条契约稳定。
> **"动态"** = 新把手、新版本、新锚点全是**加数据**，不动 Core。

## 六、四条契约的定义

### 6.1 把手契约（六步）

```
1. probe()    探测现状（运行时读取，不猜）
2. preview()  差异预览（改什么、多出多少 token、影响哪些下游）
3. backup()   备份 manifest + sha256（无备份不成写）
4. apply()    写入
5. verify()   按声明的验证策略判定生效（三态）
6. restore()  按 manifest 还原
```

**必填字段**：`id` / `title` / `target` / `writeClass` / `channel` / `privilege` / `upgradeBehavior` / **`verification`**

**可选字段**：`resolveTarget(ctx)` —— **运行时才确定目标**的把手用它覆盖静态锚点。

> 契约补充（P1c/P2a 引入）：静态锚点表达不了两类目标 —— ① 同一把手族按参数指向不同文件（`style.*` 七档）；
> ② 路径含运行时才知道的片段（C 组模板的 build hash 目录）。
> 引擎统一经 `anchorFor(h)` 取目标：有 `resolveTarget` 就用它，否则回退 `target` 锚点。
> **实测**：`style.socratic` → `style-socratic.md`；`prompt.welcomemode-*` → 挑**最高版本**目录（5.9.3），旧版本 5.8.3 原样保留。
>
> 验证按 `verification.strategy` **分流**：token-delta 走自动对照（尾段），marker-trace-grep 自己扫 trace（头部）。

> ⚠️ **命名注意**：`verification` 是**名词声明**，六步里的 `verify()` 是**动词方法**。
> 二者曾经同名，导致对象字面量里方法覆盖声明、契约校验必然失败 —— 已由自测回归用例守住（`src/selftest.mjs`）。

### 6.2 状态契约

- **文档里的结论 = 断言（assertion）**，不是数据源
- **运行时探测 = 数据源**
- 偏差 → **漂移告警**，分四类：
  - `锚点失效`（路径/键/版本找不到了）
  - `值已变`（被别人改了，如 `toneStyle`）
  - `厂商已还原`（升级覆盖了你的定制）
  - `模式相关失效`（同一文件在不同模式下可达性不同——如 `IDENTITY.md` 在专家模式下不注入）
- 断言必须是**可执行的**（能自动判定通过/失败），不是自然语言描述

### 6.3 边界契约

| 边界 | 规则 |
|---|---|
| **权限分层** | 用户目录写入自由（有备份）；**厂商文件（Program Files / 插件缓存版本目录）逐次确认** |
| **进程互斥** | 尾段通道（用户目录）可写，但提示**需新会话生效**；头部通道（C 组模板）的闸门形态**由待实测 #3 决定**——在证实"运行中不可热改"之前，**不写成硬约束**（避免把假设当事实） |
| **审计** | 每次写入进台账（触发者、时间、manifest 引用、验证结论） |
| **还原** | 一切写入可回到写入前状态 |
| **闸门** | 进程互斥未满足时，**拒绝执行**而不是"写了不生效" |

### 6.4 演进契约

**升级流程（已定）**：

```
WorkBuddy 升级
   → 走一遍既定路线（锚点校验 + 把手探测）
       ├─ 没变化  → 程序不用调整
       └─ 有变化  → 定位变化点（探针）→ 只处理变化点（重放）
```

- **锚点表**：JSON + `schemaVersion` + `migrate()`；每个 WorkBuddy 版本一份
- **锚点校验失败 = 硬报错**，绝不回退到猜测值
- **已知锚点陷阱（必须建模）**：

| 陷阱 | 事实 |
|---|---|
| `sandbox.extraAllowWrite` | 启动时被 `reconcileDesktopExtraAllowWrite()` 强制重置为内置列表 → **死把手，禁用** |
| "当前值"漂移 | `toneStyle` 文档记 `creative`，实测 `efficient` |
| C 组缓存目录 | 带 build hash（`5.9.3-wb.42398134.gd4692421.h480e8d1fee0f`）→ 版本定位必须探测 |
| A 组模板数 | 文档记 18，实测 16 → **计数类断言也要探测** |
| **身份文件静默截断** | SOUL/USER/IDENTITY 注入前**截断到 10 000 字符**，超出部分丢弃且不报错（`authority-snapshot.js:53 Ls=1e4`）→ **"文件写了"≠"模型看到了"** |
| **模式相关可达性** | `IDENTITY.md` 在**专家模式下不注入**（`authority-snapshot.js:184` `t.isExpert \|\| …`）→ 切档位会让"名字"静默消失 |
| **托管回压** | `orderedRules`（`toManagedOrderedRules`）与 `assistedApproval`（`assistedApprovalDisabled`）在服务端下发 securityCenter 时被覆盖 |

> 以上"锚点陷阱"的完整证据与出处见 **`recon-amendments.md`**。

## 七、数据流

```
[probe] → 期望状态 vs 实际状态 → [plan: 差异 + 代价]
    → 用户确认（厂商文件必须显式确认）
    → [backup: manifest + sha256]
    → [apply]
    → [verify: 三态]
         ├─ 生效       → [audit 入账]
         ├─ 未生效     → 如实报告 + 提示回滚选项
         └─ 无法判定   → 如实报告（**禁止显示为成功**）
    → [restore] 随时可用
```

### 7.1 档位 = 多把手事务（已实现）

"专家档位"是本框架上第一个**多把手事务**，规则如下：

| 原则 | 落地 |
|---|---|
| **单一用户意图 = 单一事务** | 一次切换改 3 个把手（SOUL / toneStyle / customPrompt），但用户眼里是**一个动作** |
| **一次备份覆盖全部目标** | `createBackup` 收多个 entry，且**按绝对路径去重**（toneStyle 与 customPrompt 同属 `app-config.json`，只备一次） |
| **一个期望增量** | 三个把手都在同一条 user-context 尾段通道 → 期望增量 = 各自增量**之和** |
| **一条审计** | 记 `apply-profile`（含 backupId、覆盖的把手与文件、合计期望增量） |
| **整体可还原** | `restore <backupId>` 把整套档位收回切换前——**不存在"切到一半"的中间态** |
| **事务前置校验** | 任一目标被闸门阻断或需确认 → **全部拒绝**，不做部分写入 |

档位本身是**源状态**（source state），存放在用户数据目录 `profiles/`，不进仓库（铁律 4）。
`captureProfile` 相当于 chezmoi 的 `re-add`：把 WorkBuddy 的**现状吸回源**。

## 八、目录结构

```
（仓库根）
├─ AGENTS.md              工程契约（自动加载）
├─ README.md              对外说明
├─ .gitignore             历史目录 + 防御性忽略
├─ docs/
│  ├─ product.md          定位 / 范围 / 档位 / 分期
│  ├─ framework.md        本文件
│  ├─ verification.md     验证策略 + 待实测清单
│  └─ handles.md          把手清单（实际待办）
├─ src/
│  ├─ README.md           分层说明与实现状态
│  ├─ core/               Core：契约 / 引擎 / 注册表 / 备份 / 漂移 / 锚点
│  │  └─ contracts.mjs    契约定义与校验（**只有接口，无实现**）
│  ├─ handles/            把手适配器（一个把手一个文件）
│  ├─ anchors/            锚点表（按 WorkBuddy 版本）
│  └─ verify/             验证策略实现
├─ web/                   前端静态页
└─ historicalsource/      历史侦察资料（冻结、只读、不进文档引用链以外）
```

**用户数据不在仓库内**（铁律 4）：

```
%USERPROFILE%\.workbuddy-console\
├─ profiles/      专家档位源状态（N 套 SOUL + style 内容 + toneStyle）
├─ backups/       manifest + sha256 + 原文件副本
└─ state/         审计台账、漂移记录、锚点探测缓存
```

## 九、技术栈（已定）

| 决定 | 内容 | 理由 |
|---|---|---|
| 后端 | **Node**（原生 ESM，无构建链） | 直接复用侦察期 `historicalsource/scripts/` 的 asar / CDP 能力；Windows 原生 |
| 前端 | **原生 ESM 单页**，不引框架 | 本地**特权**工具：依赖树越小，越容易审计 |
| 通信 | 本地回环 + 随机端口 + 一次性 token | 借 WorkBuddy 自己 sidecar 的鉴权模式（`randomBytes(32)` + Bearer） |
| 部署 | **无部署**——单机单用户 | 不做 Web 服务，绝不监听 `0.0.0.0` |
