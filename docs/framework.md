# 框架：怎么造

> 配套：[product](product.md)（要什么）｜[verification](verification.md)（怎么证明）｜[handles](handles.md)（有哪些面）

## 本篇主张

这里的「框架」**不是目录结构，是四条稳定契约**。前三条让它立得住，第四条让它能跟着 WorkBuddy 升级长大。骨架的判据只有一条：**加一个新的把手、适配一个新版本，应该只加数据，不动 Core**。

反面：不能直接套现成框架。Ansible / Terraform / chezmoi 都建立在「目标状态由你定义、且资源可回读」这个前提上，本项目三条里**一条都不成立**。照搬会得到一套看起来很规范、实际上天天失准的东西。

## 四条契约

| 契约 | 回答什么 | 稳定性 |
|---|---|---|
| **把手契约** | 每个可变面如何被 探测 → 预览 → 备份 → 写 → 验证 → 还原 | 不随 WorkBuddy 版本变 |
| **状态契约** | "文档=断言"如何变成可检测的期望状态与漂移告警 | 同上 |
| **边界契约** | 谁能写、何时能写、写完记哪 | 同上 |
| **演进契约** | 升级时如何**只加数据、不改框架** | 同上 |

## 为什么不能照搬现成框架

| 现实 | 后果 |
|---|---|
| 目标状态**不由我们定义**——厂商在改（模板数 18→16、`toneStyle` 漂移均已实证） | 照搬"声明式目标状态"立刻失准 |
| 效果**不可直接回读**——提示词进了 LLM，trace 还截断 | 无法像 Terraform 那样 `refresh` 读回真实状态 |
| 写操作**可能有窗口约束**——若插件缓存模板运行中不可热改（待实测 #3，**尚未证实**），则需停机写 | 没有参照系处理"目标程序运行中拒绝写"，需要自建闸门 |

**所以：借契约形状，自己长三块骨头——锚点层、验证层、闸门层。**

## 参照系选型

| 排序 | 参照 | 借什么 | 对上哪条契约 |
|---|---|---|---|
| **主选** | **chezmoi** | source state → target state；`diff` / `apply` / `--dry-run`；**`re-add`**（把现状吸回源）；`doctor` | 状态 + 档位仓 + 升级重放 |
| **次选** | **Terraform** | `plan` / `apply` 分离、**漂移检测**、provider 版本化 | 状态 + 演进 |
| **三选** | **Ansible** | module 契约：幂等 + `--check` + `--diff` + `backup` | 把手 |
| **点借** | **Home Assistant** | `schemaVersion` + 迁移函数 | 演进 |
| **自研** | — | **验证层**（见下） | 产品的护城河 |

> **选型变过一次，留档**：最初主选 Ansible（当时产品形态未定，按"改配置带护栏"猜）。形态定为"N 套档位 + 一键切换 + 升级重放"后，核心抽象变成**源状态**，chezmoi 升为主选。
> **这是"形态决定参照系"的实例**——框架服务产品，不是反过来。

**明确不选 Cockpit**（本机特权后端 + HTML 控制台）：形态太重。它唯一的价值（特权分层）用更简单的手段解决——产品自建权限分层（见边界契约），不依赖系统级 broker。

## 第五块：验证层

Ansible 写完能读回文件确认；Terraform `refresh` 能读回云资源。**而我们写完文件，不知道它有没有进 LLM。**

这块直接来自侦察期最贵的教训（**修正 1**：标记写进错存储 + trace 截断 → 误判"不进 LLM"，复测被推翻）：

- 验证是**可插拔的一等公民**，不是一个开关
- **每个把手必须声明验证策略；未声明者不允许上线**（铁律 2）
- 输出恒为**三态**：生效 / 未生效 / **无法判定**
- 详见 [verification](verification.md)

## Core / Data 分层

```
Core（框架 · 少变）—— 四条契约的接口与执行引擎，不随 WorkBuddy 版本变
├─ 契约接口定义（把手 / 状态 / 边界 / 演进）
├─ 执行引擎：plan → apply → verify → audit
├─ 备份仓 + 还原
├─ 漂移引擎（期望 vs 实际）
└─ 锚点解析器（探测失败硬报错，绝不猜）

Data（数据 · 多变）—— 加把手 / 加版本 = 只加数据
├─ 每个把手一个 adapter（含验证策略声明）
├─ 每个版本一份锚点表（schemaVersion + migrate）
└─ 每个把手一份断言表
```

> **立得住** = Core 四条契约稳定。**动态** = 新把手、新版本、新锚点全是加数据。

## 四条契约的定义

### 把手契约（六步）

```
1. probe()    探测现状（运行时读取，不猜）
2. preview()  差异预览（改什么、多出多少 token、影响哪些下游）
3. backup()   备份 manifest + sha256（无备份不成写）
4. apply()    写入
5. verify()   按声明的验证策略判定生效（三态）
6. restore()  按 manifest 还原
```

**必填字段**：`id` / `title` / `target` / `writeClass` / `channel` / `privilege` / `upgradeBehavior` / **`verification`**

**可选字段**：`resolveTarget(ctx)` —— 运行时才确定目标的把手用它覆盖静态锚点。

静态锚点表达不了两类目标：

1. 同一把手族按参数指向不同文件（`style.*` 七档）
2. 路径含运行时才知道的片段（插件缓存目录的 build hash）

引擎统一经 `anchorFor(h)` 取目标：有 `resolveTarget` 用它，否则回退 `target` 锚点。**实测**：`style.socratic` → `style-socratic.md`；`prompt.welcomemode-*` → 挑**最高版本**目录，旧版本原样保留。

验证按 `verification.strategy` **分流**：token-delta 走自动对照（尾段），marker-trace-grep 自己扫 trace（头部）。

> ⚠️ **命名坑（已踩过）**：`verification` 是**名词声明**，六步里的 `verify()` 是**动词方法**。
> 二者曾同名，导致对象字面量里方法覆盖声明、契约校验必然失败——现由自测回归用例守住。

### 状态契约

- **文档里的结论 = 断言**，不是数据源
- **运行时探测 = 数据源**
- 偏差 → **漂移告警**，五类：

| 类 | 含义 |
|---|---|
| `anchor-missing` | 锚点失效（路径 / 键 / 版本找不到了） |
| `value-changed` | 值已变（被别人改了，如 `toneStyle`） |
| `vendor-restored` | 厂商已还原（升级覆盖了你的定制） |
| `mode-dependent` | 模式相关失效（同一文件在不同模式下可达性不同） |
| `target-missing` | 目标文件不存在（升级可能清理了它） |

- 断言必须**可执行**（能自动判定通过 / 失败），不是自然语言描述

> ⚠️ **分类常量必须与实际产出同源。** 这五类冻结在 `contracts.mjs` 的 `DRIFT_KINDS` 里，而实际产出漂移的只有 `replay.detectDrift`。
> 曾出现「文档写 5 类、常量只冻 4 类、`detectDrift` 却产出第 5 类」——**这本身就是一次状态契约违例**：文档与代码各说各的，两者都没错，但没人在中间对上。
> 现由自测守住：断言 `DRIFT_KINDS` 覆盖 `replay.mjs` 里全部 `kind:` 字面量。新增漂移类时若不更新常量，自测立刻红。

### 边界契约

| 边界 | 规则 |
|---|---|
| **权限分层** | 用户目录写入自由（有备份）；**厂商文件（安装目录 / 插件缓存版本目录）逐次确认** |
| **进程互斥** | 尾段通道（用户目录）可写，提示**需新会话生效**；头部通道的闸门形态**由待实测 #3 决定**——证实之前**不写成硬约束**（避免把假设当事实） |
| **审计** | 每次写入进台账（触发者、时间、manifest 引用、验证结论） |
| **还原** | 一切写入可回到写入前状态 |
| **闸门** | 互斥未满足时**拒绝执行**，而不是"写了不生效" |

### 演进契约

```
WorkBuddy 升级
   → bundle（建重放包：只收 upgradeBehavior=invalidated 的把手）
   → drift （只读检测：哪些定制没了、哪些需要重放）
       ├─ 全 unchanged      → 程序不用调整，结束
       └─ 有 vendor-restored → replay（一次事务、一次备份）→ 各把手自己的 verify
```

**核心设计：重放包存「锚点键」，不存绝对路径。**

| 存什么 | 为什么 |
|---|---|
| `anchor`（如 `templates.style`） | 升级后路径会变（build hash 换掉），**存路径必然失效**；存锚点键才能重新定位 |
| `content` 全文 + `sha256` | 内容要能原样灌回；指纹用于检测"是否被替换" |
| `capturedFrom`（当时路径） | 仅作记录，用于报告"路径也变了" |

**实测**：收录 10 项（7 个 style + 3 个模板），正确跳过 8 项存活把手，**10 个真实文件零改动**。

**版本探测的硬边界**：升级到新版本号后，若仓库里没有对应锚点表 → **`ANCHOR_MISSING` 硬报错**并列出已有版本。这不是缺陷，是设计：**宁可拒绝运行，也不猜一个锚点表去写错地方**。新增版本 = 新增一份 `anchors/workbuddy-<ver>.json`。

**重放失败必须如实报告**：返回 `ok` / `failed` / `partial`，CLI 对部分成功显式告警并以非零退出码结束——**不允许「部分成功」被说成完成**。

### 已知锚点陷阱（必须建模）

| 陷阱 | 事实 |
|---|---|
| `sandbox.extraAllowWrite` | 启动时被 `reconcileDesktopExtraAllowWrite()` 强制重置 → **死把手，禁用** |
| "当前值"漂移 | `toneStyle` 文档记 `creative`，实测 `efficient` |
| 插件缓存目录 | 带 build hash → 版本定位必须探测 |
| 模板计数 | 文档记 18，实测 16 → **计数类断言也要探测** |
| **身份文件静默截断** | 注入前截断到 10 000 字符，超出丢弃且不报错 → **"文件写了" ≠ "模型看到了"** |
| **模式相关可达性** | `IDENTITY.md` 在专家模式下不注入 → 切档位"名字"静默消失 |
| **托管回压** | `orderedRules` 与 `assistedApproval` 在服务端下发 securityCenter 时被覆盖 |

完整证据与代码位置见 [recon-amendments](recon-amendments.md)。

### 最初基线（版本化账本）

与重放包并列的第二套快照：**每个 WorkBuddy 版本一套「出厂状态」账**（`baselines/<版本(构建哈希)>.json`），是控制台「还原」按钮的数据源。

| 规则 | 内容 |
|---|---|
| 版本键 | `版本(构建哈希)`——哈希取自插件缓存目录名（`…-wb.x.gd4692421…` → `d4692421`），运行时提取，不手填 |
| 不可覆盖 | 同版账本捕获一次后不再改写；升级出新版 → 另立新账，旧账永不被动 |
| 条目三类 | `text`（整文件把手，走把手校验写回）/ `value`（json 字段把手，只写回字段值）/ `file`（规则矩阵三域共享文件，整文件字节还原） |
| 事务 | 还原前必备份 + 闸门检查 + 审计（`restore-baseline`），与 apply 同一套语义 |
| 存放 | 项目目录 `baselines/`（gitignore 排除——铁律 4 的目的不变：公开仓库不收个人内容） |
| 与重放包的分工 | 重放包 = **用户定制**的升级找回（守护页）；最初基线 = **出厂状态**的反悔保险（个性化页） |

**控制台 UX 分层（2026-11-01 定版）**：编辑卡只留「应用」（备份→写入）与「还原」（基线写回）两键；验证能力完整保留在引擎与 API，页面不再驱动验证——生效与否由用户自建会话自测。六步契约与「验证必填」约束的是把手与引擎，不随控制台 UX 收窄。

## 数据流

```
[probe] → 期望 vs 实际 → [plan: 差异 + 代价]
    → 用户确认（厂商文件必须显式确认）
    → [backup: manifest + sha256]
    → [apply]
    → [verify: 三态]
         ├─ 生效     → [audit 入账]
         ├─ 未生效   → 如实报告 + 提示回滚
         └─ 无法判定 → 如实报告（**禁止显示为成功**）
    → [restore] 随时可用
```

### 档位 = 多把手事务

「专家档位」是本框架上第一个**多把手事务**：

| 原则 | 落地 |
|---|---|
| **单一用户意图 = 单一事务** | 一次切换改 3 个把手，用户眼里是**一个动作** |
| **一次备份覆盖全部目标** | `createBackup` 收多个 entry，**按绝对路径去重**（`toneStyle` 与 `customPrompt` 同属一个文件，只备一次） |
| **一个期望增量** | 三者同属尾段通道 → 期望增量 = 各自增量**之和** |
| **一条审计** | 记 `apply-profile`（含 backupId、把手与文件清单、合计增量） |
| **整体可还原** | `restore` 把整套收回切换前——**不存在"切到一半"** |
| **事务前置校验** | 任一目标被闸门阻断或需确认 → **全部拒绝**，不做部分写入 |

档位本身是**源状态**，存在用户数据目录 `profiles/`，不进仓库（铁律 4）。`captureProfile` 相当于 chezmoi 的 `re-add`：把现状**吸回源**。

**部分失败的处置**：`applyProfile` 逐项 try/catch，中途失败**仍写审计**（带 `status: 'partial'` 与失败清单），返回值同时给出 `written` / `failed`。
这条纪律与 `detectDrift` 同源——**先记录发生了什么，再报告成败**；否则会出现"孤儿备份 + 无台账"，用户看不到自己有东西处于半写状态。

**一处刻意的不对称**：`approval-apply` 的规则面与提示词面**不是事务**。

| | 档位切换 | 审批档位 |
|---|---|---|
| 语义 | **事务**：不存在切到一半 | **两独立面**：可能一面成一面临败 |
| 部分失败 | 逐项记录 + 审计标 `partial` | 保持混合状态，逐面报告 + 提示手工 restore |
| 为什么 | 用户眼里是**一个动作** | 两个面的**可靠性本就不同**（规则面可靠 / 提示词面只能到"文本进了请求"），强行做成事务会掩盖这个差异 |

两者都有备份兜底，都可整体还原。差异在于**要不要假装它是一个原子动作**——审批档位不假装。

## 技术栈

| 决定 | 内容 | 理由 |
|---|---|---|
| 后端 | Node（原生 ESM，无构建链） | 复用侦察期的 asar / CDP 能力；Windows 原生 |
| 前端 | 原生 ESM 单页，不引框架 | 本地**特权**工具：依赖树越小越容易审计 |
| 通信 | 回环 + 随机端口 + 一次性 token | 借 WorkBuddy 自己 sidecar 的鉴权模式 |
| 部署 | **无部署** | 单机单用户，绝不监听 `0.0.0.0` |

## 前端不变量（单页状态机的六条硬约束）

前端的形状是**单可变状态 `S` + 全量重渲染**：`render()` 一个入口，`clear(#app)` 后整棵树重建，
全站 **43 处**调用。没有框架、没有虚拟 DOM、没有局部更新。

这个形状简单，但把风险全压在一句话上——**任何只存在于 DOM 里、没进 `S` 的东西，都会在下一次 render 时消失**。
下面六条是从**实际踩过的坑**归纳出来的，不是先验推导；它们对应 `test/frontend.test.mjs` 里的断言，每条都有红灯验证。

| 编号 | 不变量 | 违反时会发生什么（实测） |
|---|---|---|
| **I1** | 用户未提交的输入必须跨 `render()` 存活 | 编辑完点「应用」，发出去的是**旧内容** → 后端判 noop → 提示「备份 null」而文件没变。**五个输入面全中过**：textarea、select、规则勾选框、厂商确认、审批确认 |
| **I2** | 写事务必须防重复提交 | 双击「应用」= 两次写入 + 两份备份；审批是双面事务，连点就是两轮 |
| **I3** | `render()` 必须纯：不许在渲染期改状态 | 渲染时顺手把 `replaySel` 初始化掉 → 数据刷新后残留旧 id → 「仅重放选中项」把**不需要重放的项**送上去 |
| **I4** | 三态永不合并，`undetermined` 不得渲染成成功 | 「无法判定」画成绿色 `✓ ?`；加载失败被渲染成空态（"还没有档位"）或永久「读取中…」 |
| **I5** | 不许用原生 `prompt` / `confirm` | 无头/自动化环境里**整页阻塞**（CDP 里表现为"点了没反应"）；且无法表达"这是危险操作"的语气 |
| **I6** | 探测缓存必须有有效期 | 页面开着时文件被外部改了，界面**一直显示旧值**——用户照着过期的"当前内容"去改，直接违反状态契约 |

**落地方式**（不是纪律，是机制）：

- I1 用 `pendingFields()` / `rememberField()` / `recallField()`，按把手隔离，换卡自动作废，写入成功后清空。
  刻意**不用"render 前后快照"**：导航离开该页时编辑器本来就不存在，快照里没有它，回来只能从状态重建——快照盖不住"往返"这一半。
- I2 用 `runBusy(fn, onError)`：**唯一置位、`finally` 唯一复位**、复位后才 render。
  ⚠️ `runBusy` 开头**不许 render**——那会冲掉 I1（这是修 I2 时引入过的新缺陷）。
- I3 把"渲染期需要的推导"改成纯计算（`effectiveSel = S.replaySel ?? needReplay`），状态收敛放到数据刷新处（`reloadAll`）。
- I6 的刷新**必须排除失败态**，否则会退回"失败 → 重试 → 再失败"的自激（实测曾一轮事件循环打满 401 次请求）。

## 置信度与限制

四条契约、Core/Data 分层、事务语义：已实现并由自测覆盖，高。

前端六条不变量：**从踩坑归纳**，每条都有断言与红灯验证，中高。局限——它们是**已发生的风险**的清单，不是完备的推导；新增第七类风险不会自动被覆盖。

参照系选型是**判断**不是事实——选 chezmoi 的理由是"核心抽象是源状态"，若产品形态再变，主选还该重估。这条留档在选型表下方。
