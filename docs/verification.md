# 验证策略层

> **这是本项目的护城河**，也是唯一没有参照系可抄的部分。
> 配套：`framework.md` 第四节（第五块）｜`product.md`（B 为魂）

## 一、为什么它是护城河

**"写进去了"和"生效了"是两回事。**

- Ansible 写完能读回文件确认；Terraform `refresh` 能读回云资源
- **我们写完文件，不知道它有没有进 LLM**——提示词进了请求**尾段**，而 trace **截断在 20003 字符**
  （`20003` 是**该次观测值，不是代码常量**——全库搜不到。结论靠"尾段必须用 token 增量法"这条**方法论**，不靠这个数字）

侦察期为回答这一个问题付出的代价（留档于 `historicalsource/docs/experiments.md` 修正史 #1）：

1. 标记写进了**错的存储**（`settings.json` ≠ `app-config.json`）→ 注入从未生效
2. 用 trace grep 找**尾段**通道 → **天然失明**，误判"不进 LLM"
3. 复测改用 **token 增量法** → 实测 +1151 tokens，**原判定被推翻**

> **结论：验证不是一个附加功能，是这个产品的存在理由。**
> 同样的错误，在没有验证器的工具里会**静默发生并且不会被发现**。

## 二、三条验证策略

| 策略 | 适用通道 | 原理 | 代价 | 可靠性 | 已实证 |
|---|---|---|---|---|---|
| **标记法 / trace grep** | 请求**头部**（C 组 `prompt.tpl`、fragments） | 注入唯一标记，在新 trace 里 grep | 低（一次会话） | **高**（头部不被截断） | ✅ `WBPROBE-FRAGMENT-888`<br>✅ **已自动化**（P2a） |
| **token 增量法** | 请求**尾段**（user-context：SOUL / 身份 / 风格 / 指令） | **单变量对照**：改前基线 vs 改后，比较 `prompt_tokens` 增量与理论值 | 中（**要跑真实会话、烧真 token**） | **高**（唯一对尾段有效） | ✅ 身份 +1523 / 指令 +1151<br>✅ **已自动化**（下端） |
| **渲染日志法** | 会话启动时的渲染产物 | 读主进程日志 `Rendered user-context (N chars)` / `Injected custom prompt (N chars)` | 低 | 中（证明"渲染了"，**不证明"进了请求"**） | ✅ |
| **重启后回读** | 配置值 / 规则矩阵 | 写入 → 回读 → **重启** → 再回读 | 低 | **高**（专捕"启动覆盖"类陷阱） | ✅ **已实现**（P2b） |

### 重启后回读：为什么必须两阶段（P2b 实测确立）

写完立刻读回**永远是对的**（刚写的就是那份），所以"读回一致"证明不了任何事。
真正的风险是 **WorkBuddy 启动时把值重置回默认** —— `reconcileDesktopExtraAllowWrite()` 就是这么干的。

| 阶段 | 判定 |
|---|---|
| **阶段 1**（写完立即读回） | 证明"确实写进去了"；但结论只能是 `undetermined`，因为还没重启 |
| **阶段 2**（重启后再读） | 指纹仍一致 → `effective`；被还原 → **`ineffective`** |

`ineffective` 在这里的含义很关键：**不是"没写进去"，而是"写进去又被抹掉了"**。这正是 `extraAllowWrite` 那类坑的判据。
状态存 `<用户数据目录>/state/readback/<key>.json`，因为"重启后再读"跨越了两次进程调用。

### 选择规则

```
请求头部通道   → 标记法（便宜、够用）      ← 已实现 src/verify/marker.mjs
请求尾段通道   → token 增量法（唯一可靠）  ← 已实现 src/verify/token-delta.mjs
配置值 / 规则面 → 重启后回读（专治 extraAllowWrite 那类"启动被抹掉"）
```

> **禁止**用 trace grep 判尾段通道的负结果——**截断导致的"零命中"是假阴性**，不是证据。
> 引擎按把手的 `verification.strategy` **分流**：只有 token-delta 走自动对照，标记法自己扫 trace。

### 标记法的三条硬保护（P2a 实测确立）

| 保护 | 为什么 |
|---|---|
| **逐条时间过滤** | trace 文件持续追加：文件的 mtime 可能是新的，但里面的记录可能是旧的。只按文件 mtime 过滤，会把**改动前的旧标记**误当成新证据 |
| **无时间戳 → undetermined** | 不拿文件 mtime 冒充行时间（那是猜）。找到标记但无从判断时间先后时，如实说"无法判定" |
| **没 apply 过 → undetermined** | 从未改过就去 grep，得到的"未生效"毫无意义。这不是"未生效"，是"根本没做过这件事" |

### 成本纪律

- **验证按需手动触发**，不后台自动跑（每次验证要跑真实会话、烧真 token）
- 同一次验证尽量**批量覆盖多个变量**，但判定必须**单变量**（否则无法归因）
- 基线要新鲜：**改前当次测**，不复用别次会话的 token 数

### 自动对照流程（P0b 已实现，见 `src/verify/auto-capture.mjs`）

`verify` 不再需要手工填数字：

1. `apply` 时把**期望增量**（按**截断后**文本算）与**时间戳**写进审计台账
2. `verify` 从台账取该把手最近一次 `apply`
3. 在 `traces/<worker-pid>/trace_*.jsonl` 里按**会话**取样本
4. 交给 token-delta 判定

**为什么按「会话」而不是「时间上最近的一条请求」**

| 现象 | 后果 |
|---|---|
| 同一会话内 `prompt_tokens` 随历史累积**逐轮增长**（本机实测：34826 → 35271 → 38430 → 38610） | 取"最近一条"会把**历史长度**混进增量 → 归因失效 |
| ⇒ 必须取**会话首条**请求 | 它才代表"静态前缀 + user-context + 首条提问"，才是可比量 |

**四条硬保护**（全都在防"假阴性"）：

| 保护 | 为什么 |
|---|---|
| **按会话起点切分** | 会话起点取自 `traces/<worker>/` 的**目录创建时间**（本机实测：与首条请求相差 27–250 ms）。**会话在改动前就已创建 ⇒ 它的 user-context 是旧的 ⇒ 整个排除出观测池**——而不是把它的 Δ≈0 判成"未生效" |
| **排除非聊天请求** | 标题生成走 `wb-lite`（约 517 tokens 的静态提示词），混入会污染基线 |
| **排除异常样本** | `prompt_tokens = 0`、`finish_reason = content_filter`（L4 被拦腰切断时 usage 清零） |
| **截断后算期望** | 身份文件有 10 000 字符上限（见 `recon-amendments.md`），按全量文本算期望会偏大 |

**附加告警**：基线与观测**模型不同**（静态前缀不同，不可归因）；会话起点只能退回"首条请求时间"时（拿不到目录创建时间）标注为**次优信号**。

**用户侧动作**：改完 → 在 WorkBuddy 里**新建会话**并发一条消息 → 再 `verify`。
若只在旧会话里续聊，工具明确说"请新建会话"，**不判"未生效"**。

诊断数据源：`node src/cli.mjs traces`。

## 三、三态输出（硬规则）

| 态 | 含义 | 表现 |
|---|---|---|
| **生效** | 有证据证明改动进入了目标链路 | 绿 |
| **未生效** | 有证据证明**没**进入 | 红 |
| **无法判定** | 证据不足（样本太小、会话失败、通道不可测） | **黄，并明确写"无法判定"** |

> **禁止把"无法判定"显示成成功。** 这是产品可信度的底线（铁律 6）。
> 侦察期的教训正是：一个"零命中"被当成了"不进 LLM"的证据。

## 四、策略声明为必填

把手适配器必须声明（字段名 `verification`，**名词**，与动词方法 `verify()` 区分）：

```js
verification: {
  strategy,   // 'marker-trace-grep' | 'token-delta' | 'render-log' | 'readback-after-restart'
  channel,    // 'request-head' | 'request-tail' | 'rule-matrix' | 'config-value'
  baseline,   // 如何取基线
  assertion,  // 判据（可与理论值比较）
}
```

**未声明验证策略的把手不允许上线**（铁律 2）。

### 第 4 条单独说明（本项目最重要的待验证假设）

它是"审批自动同意"这件事**能不能成**的分水岭：

- **若结论是"能治"** → 提示词面的放宽可信
- **若结论是"治不了"**（模型自身对齐，上游）→ **这个承诺必须收缩**

> **把这个"治不了"如实报出来，本身就是产品的价值。** 用户不会再有"是不是我配错了"的怀疑。

### 双面编排：为什么"审批自动同意"永远不可能被完全验证

P3 把它拆成两个面，各自的可信度**根本不同**：

| 面 | 能验证到什么 | 可信度 |
|---|---|---|
| **规则面**（`orderedRules`） | 重启后回读：规则还在不在 | ✅ **可靠** |
| **提示词面**（`personal_files_safety`） | 标记法：文本进没进请求 | ⚠️ **只能到这一步** |

**关键**：提示词面即使证明"文本进了请求"，也**证明不了"模型不再自己问"**。
后者取决于模型自身对齐（上游），客户端任何改动都触不到。

因此 `verifyApproval` **不返回单一结论**，而是逐面报告 + 合成一个诚实三态：
任一面未生效 → `ineffective`；有面无法判定 → `undetermined`；全成立 → `effective`（但仍带免责说明）。

## 六、方法论纪律（来自侦察期教训）

1. 请求**头部**通道 → 标记法 / trace grep
2. 请求**尾段**通道 → **一律 token 增量法**（单一变量对照）
3. **任何"当前值"都必须现读**，不得引用文档里的快照
4. **负结果要区分真假**：截断导致的零命中 = 假阴性，**不是证据**
5. **判定被推翻时留修正记录**，不静默改数（侦察期的修正史是资产，不是污点）
