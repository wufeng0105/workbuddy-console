# 验证：怎么证明

> **这是本项目的护城河**，也是唯一没有参照系可抄的部分。
> 配套：[framework](framework.md) 的"第五块"｜[product](product.md) 的「B 为魂」

## 本篇主张

**「写进去了」和「生效了」是两回事。** 而这个产品的全部价值，建立在能把这件区分做出来。所以验证不是一个附加功能，它是**这个工具存在的理由**——同样一个错误，在没有验证器的工具里会静默发生、并且永远不会被发现。

反面：验证只能证明**链路**，不能证明**效果**。「文本进了请求」是能证明的，「模型因此改变了行为」不是。把后者当成前者的推论，是这套东西最容易被误用的地方。

## 为什么它是护城河

难的不是"读回文件"，是**读回之后没有任何东西能告诉你它进了请求没有**。
提示词走请求的**尾段**，而 trace 是截断的——**尾段内容根本没有完整落盘**，
所以"grep 一遍没找到标记"这件事**不构成证据**（框架篇已用 Ansible/Terraform 的对照说明为什么需要这一层，此处不重复）。

> 侦察期观测到的截断值 `20003` 是**该次观测值，不是代码常量**（全库搜不到）。
> 真正的结论是**方法论**——「尾段通道必须用 token 增量法」，它不依赖这个数字。

侦察期为这一个问题付出的代价（见 [recon-baseline/findings/10-experiments](../recon-baseline/findings/10-experiments.md) 修正 1）：

1. 标记写进了**错的存储**（`settings.json` ≠ `app-config.json`）→ 注入从未生效
2. 用 trace grep 找**尾段**通道 → **天然失明**，误判"不进 LLM"
3. 复测改用 **token 增量法** → 实测约 +1.1k tokens，**原判定被推翻**（两个记录的数字不同，只作约数，见 [recon-amendments](recon-amendments.md)「记录 1」）

**同样的错误，在没有验证器的工具里会静默发生。**

## 三种有实现的验证策略

| 策略 | 适用通道 | 原理 | 代价 | 可靠性 |
|---|---|---|---|---|
| **标记法** | 请求**头部** | 注入唯一标记，在新 trace 里 grep | 低（一次会话） | **高**（头部不被截断），但对普通编辑只能判"无法判定"，见 R1 |
| **token 增量法** | 请求**尾段** | **单变量对照**：改前基线 vs 改后，比 `prompt_tokens` 增量与理论值 | 中（跑真实会话、烧真 token） | **对大改动高；对小改动不成立**——实测会话间噪声下限 ≥ 26 tokens，而 35 tokens 量级改动的判定窗口只有 ±10.5 tokens（残余 R26） |
| **重启后回读** | 配置值 / 规则矩阵 | 写 → 回读 → **重启** → 再回读 | 低 | **高**（专捕"启动覆盖"类陷阱） |

> 契约枚举里还有第四个 `render-log`——**它没有实现，也没有任何把手使用**（残余 R2）。
> 本表只列有实现的三条，别的地方也不许再出现"四种策略"。
>
> 标记法的可靠性有一个前提：模板里得有我们能认出的标记。而 `apply` **从不注入标记**
> ——用户正常编辑写的是自己的内容，所以它对普通编辑只能判 `undetermined`（残余 R1）。
> 判"未生效"会把"没测"说成"没生效"，是更坏的错。

### 选择规则

```
请求头部通道   → 标记法（便宜、够用）      ← src/verify/marker.mjs
请求尾段通道   → token 增量法（唯一可靠）  ← src/verify/token-delta.mjs
配置值 / 规则面 → 重启后回读（专治"启动被抹掉"）← src/verify/readback.mjs
```

> **禁止**用 trace grep 判尾段通道的负结果——**截断导致的"零命中"是假阴性**，不是证据。
> 引擎按把手的 `verification.strategy` **分流**：只有 token-delta 走自动对照，标记法自己扫 trace。

## 判据什么时候会给出错答案

这一节是本篇最该先读的部分。**声明了验证策略，不等于策略能给出答案**——而且它出错时不报错，只是安静地把答案给错。

下面每一条都是 2026-11-02 独立复核在真实代码上实测出来的。列在这里，是因为**下一处同类错误一定长得像其中之一**。
**哪几条已经真的堵上、哪几条还没有，以 [DOC-OUTLINE](../DOC-OUTLINE.md) 残余 R1/R3 为准**——
本篇只描述错误长什么样，不逐条声明"已修"，避免出现第二份兑现状态。

### token 增量法的三个方向性错判

判据的核心是一句：`|实测Δ − 期望Δ| / |期望Δ| ≤ 30%` 判生效。这句话在三个方向上都会错：

| 症状 | 表现 | 根因 | 现在 |
|---|---|---|---|
| **删减改动永远判不出「生效」** | 删 60 token、实测 Δ-60 → 判「未生效」 | 噪声带用了**带符号**的 `delta <= 3`，负值恒成立 | 改用 `Math.abs(delta)` |
| **小改动被判「未生效」** | 期望 +7、实测 0 → 判「改动未进入请求」 | `MIN_MEANINGFUL` 只用来拼提示语，**没进判定** | 低于判定下限时给 `undetermined` |
| **小改动的「吻合」也被吞成「判不了」** | 期望 +12、实测 +12 → 判 `undetermined` | 上一行修法的**过度反应**：把「吻合」也当成「太小」 | 吻合就判生效，但如实标「敏感度低」 |
| **真实异常被说成「噪声」** | 期望 +19、实测 **-3000** → 说「无法与样本噪声区分」 | 同上 | 大偏差标 `anomaly`，明说「可能有别的变量」 |

> 这一格值得记住：**同一个判定改了三次才对**——先给假确定性，再给假不确定，最后才分三路。
> 真值判据不是一次写对的，是靠「注入回归→断言必须变红」逼出来的。

### 「没改动」被当成「已生效」

`noop`（内容与现状一致）曾把 `expectedDeltaTokens` 记成 `0`，
于是 verify 读到 `0` → 「预期无变化 + 实测无变化」→ 回 **`effective`**。
**用户什么都没改，工具报绿色「✅ 生效」。**

现在：noop 记 `null`（没有可验证的期望），verify 见到 noop 记录直接判 `undetermined`。

### 规则面：策略存在但没有任何用户可达路径

`readback-after-restart` 需要 `restarted: true` 才能给出结论。而这个参数：

- CLI 的 `verify` 子命令**不解析**它（只有 `--baseline/--observed/--expected`）
- 前端**根本不调**把手级 verify

结果：规则面的验证**永远停在「无法判定」**，还提示用户「再运行一次 verify（带 restarted 参数）」——
一个用户拿不到的参数。现在 CLI 接受 `--restarted`（含 `=true` / 空格形式），并在无法判定时打印**可直接复制的完整命令**。

### 标记法：对普通编辑必然判「未生效」

标记法的前提是模板里含一个我们能认出的标记。但 **apply 从不注入标记**——用户正常编辑写的是自己的内容。
于是 verify 拿常量前缀去 grep，**必然找不到** → 判 `ineffective`（未生效）。
这是把"没测"说成"未生效"：用户明明改对了，工具说他没生效。

实测旁证：真实 6 个 `prompt.tpl` 全部 `hasMarker = False`。

现在：模板里没有标记时**直接判 `undetermined` 并说清原因**，不再 grep 一个必然落空的东西。
代价是——**提示词模板类把手无法自动验证**，只能人工确认。这条写进 [DOC-OUTLINE](../DOC-OUTLINE.md)「已知残余」。

### 一条判据的三个必要条件

从上面这些错误反推，一条判据要说得出「答案」，必须同时满足：

| 条件 | 反例 |
|---|---|
| **可达**：用户拿得到调用它的方式 | `restarted` 参数没暴露 → 规则面永远不可达 |
| **方向正确**：正负增量的判定对称 | 带符号比较 → 删减永远判负 |
| **拒绝假确定**：判不了就说判不了，不猜 | 小增量硬判 → 假确定；一律判不了 → 假不确定 |

缺任何一条，判据就退化成「装饰」——看着有，答不出。

## 为什么"重启后回读"必须两阶段

写完立刻读回**永远是对的**——刚写的就是那份。所以"读回一致"证明不了任何事。

真正的风险是 **WorkBuddy 启动时把值重置回默认**。`reconcileDesktopExtraAllowWrite()` 就是这么干的。

| 阶段 | 判定 |
|---|---|
| **阶段 1**（写完立即读回） | 证明"确实写进去了"；但结论只能是 `undetermined`，因为还没重启 |
| **阶段 2**（重启后再读） | 指纹仍一致 → `effective`；被还原 → **`ineffective`** |

**`ineffective` 在这里的含义很关键**：不是"没写进去"，而是**"写进去又被抹掉了"**。这正是 `extraAllowWrite` 那类坑的判据。

状态存 `<用户数据目录>/state/readback/<sha256(key) 前 16 位>.json`（`src/verify/readback.mjs` 的文件名是真身哈希，不是 key 原文——key 里可能有 `/` 等路径字符），因为"重启后再读"跨越了两次进程调用。

## 标记法的三条硬保护

| 保护 | 为什么 |
|---|---|
| **逐条时间过滤** | trace 文件持续追加：文件 mtime 可能是新的，但里面的记录可能是旧的。只按文件 mtime 过滤，会把**改动前的旧标记**误当成新证据 |
| **无时间戳 → `undetermined`** | 不拿文件 mtime 冒充行时间（那是猜）。找到标记但无从判断时间先后时，如实说"无法判定" |
| **没 apply 过 → `undetermined`** | 从未改过就去 grep，得到的"未生效"毫无意义。这不是"未生效"，是**"根本没做过这件事"** |

## 自动对照：token 增量法怎么自动跑

`verify` 不需要手工填数字：

1. `apply` 时把**期望增量**（按**截断后**文本算）与**时间戳**写进审计台账
2. `verify` 从台账取该把手最近一次 `apply`
3. 在 `traces/<worker-pid>/trace_*.jsonl` 里按**会话**取样本
4. 交给 token-delta 判定

### 为什么按「会话」而不是「时间上最近的一条请求」

| 现象 | 后果 |
|---|---|
| 同一会话内 `prompt_tokens` 随历史累积**逐轮增长**（实测：34826 → 35271 → 38430 → 38610） | 取"最近一条"会把**历史长度**混进增量 → 归因失效 |
| ⇒ 必须取**会话首条**请求 | 它才代表"静态前缀 + user-context + 首条提问"，才是可比量 |

### 五条硬保护

全都在防"假阴性 / 假阳性"：

| 保护 | 为什么 |
|---|---|
| **按会话起点切分** | 起点取自 `traces/<worker>/` 的**目录创建时间**（实测与首条请求相差 27–250 ms）。会话在改动前就已创建 ⇒ 它的 user-context 是旧的 ⇒ **整个排除出观测池**，而不是把它的 Δ≈0 判成"未生效" |
| **按模型隔离** | 不同模型的静态前缀与分词器不同，**跨模型算增量毫无意义** → 自动锁定"改动前最后一次聊天所用的模型"，其它样本排除并报告数量。本机 trace 里实际出现过**至少五种**模型，其中 `hy3` 既不在文档、也不在当前排除表里（残余 R14）。**种数一律现读 `node src/cli.mjs traces`，本组文档不写死** |
| **排除非聊天请求** | `wb-lite`（标题生成）与 `step-5-preview`（规模随任务变）都不参与主聊天链路 |
| **排除异常样本** | `prompt_tokens = 0`、`finish_reason = content_filter`（L4 被拦腰切断时 usage 清零） |
| **截断后算期望** | 身份文件有 10 000 字符上限，按全量文本算期望会偏大 |

> **「按模型隔离」这条是真实数据验证才发现的**：fixture 里只有单一模型，跑得再多次也暴露不出来。
> 真实数据（560 条 generation / 50 个会话）一跑就现形——**"fixture 通过"不等于"现实成立"**。

**附加告警**：基线与观测模型不同（静态前缀不同，不可归因）；会话起点只能退回"首条请求时间"时标注为**次优信号**。

**用户侧动作**：改完 → 在 WorkBuddy 里**新建会话**并发一条消息 → 再 `verify`。
只在旧会话里续聊时，工具明确说"请新建会话"，**不判"未生效"**。

诊断数据源：`node src/cli.mjs traces`。

## 三态输出（硬规则）

| 态 | 含义 | 表现 |
|---|---|---|
| **生效** | 有证据证明改动进入了目标链路 | 绿 |
| **未生效** | 有证据证明**没**进入 | 红 |
| **无法判定** | 证据不足（样本太小、会话失败、通道不可测） | **黄，并明确写"无法判定"** |

> **禁止把"无法判定"显示成成功。** 这是产品可信度的底线（铁律 6）。
> 侦察期的教训正是：一个"零命中"被当成了"不进 LLM"的证据。

## 策略声明为必填

把手必须声明（字段名 `verification`，**名词**，与动词方法 `verify()` 区分）：

```js
verification: {
  strategy,   // 'marker-trace-grep' | 'token-delta' | 'render-log' | 'readback-after-restart'
  channel,    // 'request-head' | 'request-tail' | 'rule-matrix' | 'config-value'
  baseline,   // 如何取基线
  assertion,  // 判据（可与理论值比较）
}
```

**未声明验证策略的把手不允许上线**（铁律 2）。

## 双面编排：为什么"审批自动同意"永远无法被完全验证

P3 把它拆成两个面，各自可信度**根本不同**：

| 面 | 能验证到什么 | 可信度 |
|---|---|---|
| **规则面**（`orderedRules`） | 重启后回读：规则还在不在 | ✅ **可靠** |
| **提示词面**（`personal_files_safety`） | 标记法：文本进没进请求 | ⚠️ **只能到这一步** |

**关键**：提示词面即使证明"文本进了请求"，也**证明不了"模型不再自己问"**。后者取决于模型自身对齐（上游），客户端任何改动都触不到。

因此 `verifyApproval` **不返回单一结论**，而是逐面报告 + 合成一个诚实三态：任一面未生效 → `ineffective`；有面无法判定 → `undetermined`；全成立 → `effective`（但仍带免责说明）。

### 第 4 条单独说明

它是"审批自动同意"能不成成的分水岭：

- 若"能治" → 提示词面的放宽可信

> **把这个"治不了"如实报出来，本身就是产品的价值。** 用户不会再有"是不是我配错了"的怀疑。

## 方法论纪律

这是从侦察期教训里固化下来的，写进文档是因为它**比任何一条结论都耐用**：

1. 请求**头部**通道 → 标记法 / trace grep
2. 请求**尾段**通道 → **一律** token 增量法（单一变量对照）
3. **任何"当前值"都必须现读**，不得引用文档里的快照
4. **负结果要区分真假**：截断导致的零命中 = 假阴性，**不是证据**
5. **判定被推翻时留修正记录**，不静默改数（修正史是资产，不是污点）

### 同一套纪律也适用于代码，不只是验证结论

上面五条讲的是「怎么测 WorkBuddy」。但本项目自己也吃过同类的亏——**契约写在文档里，代码没跟上，而没有任何东西在中间把它揪出来**。

一次独立只读审计列出 12 条，核实后 1 条误报、9 条成立。其中两条不是笔误，是**真的会把用户置于不可知状态**：

| 症状 | 本质 |
|---|---|
| 文档写「漂移 5 类」、`DRIFT_KINDS` 只冻 4 类、`detectDrift` 却产出第 5 类 | 分类常量与实际产出不同源 |
| `applyProfile` 循环裸 `await`，中途失败时审计永不写 | 备份已存在、文件已半写，但台账里查不到 |

两者的共同点：**每份材料单独看都对，合起来才错**——和「多篇成组」里说的病是同一个。

**处置方式是给它们各配一条自测断言**，而不是改完就算：

| 断言 | 守的是什么 |
|---|---|
| `DRIFT_KINDS` 覆盖 `replay.mjs` 全部 `kind:` 字面量 | 新增漂移类却不更新常量 → 立刻红 |
| `applyProfile` 部分失败仍写审计且带 `status`/`failed` | 「孤儿备份 + 无台账」复发 → 立刻红 |
| `writeDomainRules` 在 path 含 `]` 时仍能正确收尾 | 正则截断写坏 `settings.json` → 立刻红 |

> **没有测试守住的修复会退回去。** 这三条不是「多写了几个测试」，是把一次审计的结论变成**下次不再需要重新发现**的东西。
>
> 剩下六条（CLI 输出恒假条件、字段名不符、死代码、远程字体、令牌留在 URL）不配断言——它们是**一眼可辨的实现错误**，不是契约层面的错配。判断标准见 `AGENTS.md` 的「本项目自己的坑」。
